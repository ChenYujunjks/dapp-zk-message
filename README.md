# ZK Message DApp

A full-stack zero-knowledge messaging DApp built with Next.js, thirdweb, Solidity, and Groth16 zk-SNARKs.

Users can send on-chain messages only after generating a valid zk proof. The proof is generated by the Next.js backend and verified on-chain by a Solidity Groth16 verifier contract.

## Tech Stack

- Next.js
- TypeScript
- thirdweb SDK
- Solidity
- Hardhat
- Circom
- snarkjs
- Groth16 zk-SNARK
- Polygon / thirdweb deployment

## Smart Contracts

This project contains two main contracts:

### `Groth16Verifier.sol`

The verifier contract generated from the Circom circuit using `snarkjs`.

It verifies the Groth16 proof on-chain.

### `MyContract.sol`

The main messaging contract.

It stores received messages and verifies that each message is submitted with a valid zk proof.

Main functions:

- `sendMessageWithProof(...)`
- `receiveMessagesContentWithSender(address)`
- `updateMerkleRoot(uint256)`
- `computeMessageHash(string)`

## ZK Circuit

The circuit proves that the sender has valid membership in a Merkle tree and binds the proof to a specific message.

Public signals:

```txt
root
messageHash
nullifierHash
```

Private inputs:

```txt
leaf
pathElements
pathIndices
nullifier
```

The contract stores the Merkle root and verifies that the proof matches:

```txt
[merkleRoot, messageHash, nullifierHash]
```

## Message Sending Flow

```txt
1. User enters recipient address and message content in the frontend.
2. Frontend sends the message content to the Next.js backend API.
3. Backend runs the zk proof generation logic using snarkjs.
4. Backend returns:
   - pA
   - pB
   - pC
   - nullifierHash
5. Frontend uses thirdweb SDK to call MyContract.sendMessageWithProof(...)
6. MyContract recomputes messageHash on-chain.
7. MyContract calls Groth16Verifier.verifyProof(...)
8. If the proof is valid, the message is stored for the recipient.
9. Recipient reads messages through receiveMessagesContentWithSender(address).
```

## Frontend Contract Interaction

The frontend uses the thirdweb SDK to connect to the deployed `MyContract`.

```ts
import { prepareContractCall } from "thirdweb";

const transaction = prepareContractCall({
  contract,
  method:
    "function sendMessageWithProof(address _to, string _content, uint256[2] _pA, uint256[2][2] _pB, uint256[2] _pC, uint256 _nullifierHash)",
  params: [recipient, content, pA, pB, pC, nullifierHash],
});
```

## Backend Proof Generation

The backend receives the message content and generates the zk proof.

```txt
POST /api/generate-proof
```

The backend computes:

```txt
messageHash = sha256(content) % FIELD_SIZE
nullifierHash = Poseidon(nullifier, messageHash)
```

Then it generates a Groth16 proof using:

```txt
merkle_message.wasm
merkle_message_final.zkey
```

The returned proof parameters are formatted for Solidity, including reversing the `pB` coordinates required by the Solidity verifier.

## Deployment

The contracts are deployed using thirdweb.

Deployment order:

```txt
1. Deploy Groth16Verifier.sol
2. Copy the deployed verifier address
3. Deploy MyContract.sol with:
   - _verifier = deployed Groth16Verifier address
   - _merkleRoot = circuit Merkle root
```

## Local Development


```bash
pnpm dev
```

Test proof generation:

```bash
npx tsx src/server/scripts/verify-proof.ts
```

## Current Limitations

- The current version uses a fixed demo Merkle tree.
- The nullifier strategy is basic and should be improved for production.
- Proof generation runs on the Next.js backend.
- This is a demo/research implementation and has not been audited.
